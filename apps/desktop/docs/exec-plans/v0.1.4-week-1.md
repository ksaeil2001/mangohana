# Trio v0.1.4 — 이번 주 P0·P1 실행 계획

> 2026-09-17 범위 갱신: 이 문서의 macOS 항목은 **non-MVP / future scope**이며 현재 MVP 지원이나 Release Gate 요구가 아닙니다. Linux 범위는 변경하지 않습니다. [현재 플랫폼 정책](../operations/mvp-platform-scope.md)을 우선합니다.
> 이전 시점의 실행 결과와 gate 상태는 역사적 기록이며 현재 후보 판정은 [최신 Release Gate 보고서](../release/2026-09-17-mvp-release-gate.md)를 따릅니다.

> **계획 상태:** 이번 주 착수용 실행 계약  
> **기준 버전:** v0.1.3 공개 릴리스  
> **목표:** 새 기능을 확장하기 전에 설치·업데이트·프로젝트 저장의 신뢰성을 상용 운영 기준으로 끌어올린다.

## 1. 이번 주의 완료 정의

이번 주는 v0.1.4를 바로 배포하는 주가 아니라, **서명·업데이트·공급망·저장 안정성의 구현과 외부 의존성을 분리하고, 다음 개발 주기에 막힘 없이 들어갈 수 있는 검증 가능한 기준선**을 만드는 주다. 코드 서명 인증서, Apple 개발자 계정, 법률 검토, 실제 테스트 장비가 필요한 항목은 “완료”가 아닌 “외부 승인 대기”로 명확히 분리한다.

| 결과물 | 이번 주 종료 시 기대 상태 |
| --- | --- |
| 릴리스 보안 설계 | Windows·macOS 서명/공증에 필요한 credential map, CI secret 이름, 태그 릴리스 게이트, 검증 명령이 문서화되고 dry-run 경로가 준비됨 |
| 업데이트 QA | v0.1.3 → v0.1.4 후보 전환 시나리오, 실패·재시도·복구 관찰 표, 로그 수집 방식이 준비됨 |
| 공급망 가시성 | checksum·SBOM·빌드 검증 결과를 Release 자산으로 만드는 스크립트와 워크플로우 변경안이 PR 단위로 준비됨 |
| 상용 운영 문서 | LICENSE·개인정보 처리 방침 초안의 빈 운영 정보와 EULA·보안·지원 문서의 확정 책임자가 식별됨 |
| P1 검증 기준선 | 세션·revision·원자 저장 구현을 재작성하지 않고, 기존 테스트와 Windows 실증의 잔여 공백이 명확해짐 |
| 패키지 브랜딩 | 아이콘·앱 메타데이터 요구사항과 수용 기준이 확정되고 플랫폼 패키지 반영 작업이 시작됨 |

## 2. 현재 기반과 이번 주의 판단

P1-01부터 P1-03은 단순한 미래 아이디어가 아니다. 현재 코드에는 `projectSessions.ts`, `projectRevision.ts`, `projectSaveTransaction.ts`, `projectRecovery.ts`, `projectProtection.ts`가 존재하며, Electron 시작 경로에는 single-instance lock과 second-instance focus가 구현되어 있다. 관련 단위 테스트도 존재한다. 따라서 이번 주에는 세션·revision·저장 구조를 처음부터 재구현하지 않는다. 먼저 현재 구현 계약과 Windows 실증 범위를 대조하고, 검증 공백 또는 실제 결함만 작은 후속 PR로 처리한다.

반대로 P0-01, P0-02, P0-03, P0-04와 P1-04는 외부 credential·운영 정보·새 배포 자산 또는 파이프라인 변경이 필요하다. 이 항목들은 **준비 작업과 외부 승인 대기 작업을 병렬화**한다.

## 4. 일자별 실행 순서

### Day 1 — 기준선 고정과 외부 의사결정 요청

Day 1에는 `main` 기준으로 전체 테스트, 타입 검사, 빌드, 현행 멀티플랫폼 패키지·Release 자산 목록을 다시 기록한다. 이는 이후 서명·SBOM·브랜딩 변경이 기존 문제를 만들지 않았다는 기준선이 된다. 동시에 다음 외부 결정을 한 번에 요청한다.

| 결정 | 필요한 값 | 없을 때의 처리 |
| --- | --- | --- |
| Windows 서명 | 인증서 공급 방식(PFX 또는 클라우드 서명), 발급 주체, 보관 책임자 | unsigned preview 빌드만 허용하고 stable 태그 배포는 차단 |
| macOS 공증 | Apple Developer Team ID, Developer ID Application 인증서, 공증용 앱 전용 비밀번호 또는 API key | DMG·ZIP 수동 설치 자산만 허용하고 macOS 자동 업데이트는 비활성 상태 유지 |
| 법률·지원 | 운영 주체명, 관할지, 개인정보 문의 이메일, 보안 신고 채널, 지원 SLA | 모든 법률 문서를 “초안”으로 유지하고 유료 판매/조직 계약 금지 |
| 브랜드 | 아이콘 원본, 상표 사용 범위, 앱 표기명, Linux 카테고리 | 기본 아이콘을 유지하되 새 브랜드 자산 패키징 PR은 병합하지 않음 |

Day 1 종료 기준은 각 의사결정이 **확정됨 / 담당자 배정됨 / 차단됨** 중 하나로 분류되고, 기준선 명령 결과가 기록되는 것이다.

```bash
npm test
npm run typecheck
npm run build
npm run smoke:ipc
npm run smoke:storage
```

### Day 2 — 공급망 자산과 서명 게이트 구현 시작

스트림 A와 C는 분리된 PR로 작업한다. 첫 PR은 릴리스 출력 디렉터리에서 `SHA256SUMS.txt`, 패키지·Node 의존성 SBOM, 빌드 검증 요약을 생성한다. checksum은 `.exe`, `.dmg`, `.zip`, `.AppImage`, 업데이트 메타데이터 각각을 포함해야 하며, Release job은 이 파일이 없으면 실패해야 한다. SBOM 형식은 CI의 잠긴 Node/npm 환경에서 재현 가능한 형식으로 선택하고, 생성 명령·도구 버전을 문서화한다.

두 번째 PR은 태그 Release에만 서명·공증을 요구하는 게이트를 만든다. PR과 `main` 패키징은 credential 없이도 검증 가능해야 하지만, stable `v*` 태그는 필요한 credential이 없을 때 unsigned 자산을 조용히 게시해서는 안 된다. Windows는 서명 후 `signtool verify`로, macOS는 `codesign --verify --deep --strict`, `spctl`, 공증 결과로 검증한다. 비밀값은 저장소 파일, 로그, Artifact, Release 노트에 출력하지 않는다.

| 변경 후보 | 책임 | 수용 기준 |
| --- | --- | --- |
| `scripts/generate-release-provenance.mjs` | checksum·SBOM·검증 요약 생성 | 동일 잠금 파일에서 재실행 시 포맷이 안정적이고 모든 배포 파일을 열거 |
| `scripts/verify-release-assets.mjs` | checksum과 필수 파일 검사 | 누락·불일치·예상 밖 파일에서 non-zero 종료 |
| `.github/workflows/package-release.yml` | 자산 생성·업로드·태그 게이트 | provenance 자산을 Artifact와 Release에 포함, stable 배포의 unsigned fallback 차단 |
| `docs/operations/release-signing.md` | credential map·rollback·검증 절차 | secret 이름만 기록하고 비밀값·인증서 원문은 기록하지 않음 |

### Day 3 — 업데이트 전환 시험과 P1 계약 감사

스트림 B는 업데이트 전환 시험을 자동화와 수동 관찰로 나눈다. 먼저 `createAutoUpdateController`의 현재 단위 테스트가 체크·다운로드·진행률·오류·명시적 설치를 충분히 다루는지 매트릭스로 정리한다. 그 다음 v0.1.3 설치본에서 v0.1.4 후보를 감지하는 실제 시나리오를 준비한다. 후보 버전 전략은 electron-updater의 prerelease 채널 동작을 확인한 뒤 결정하며, stable 사용자가 실험용 빌드를 받지 않도록 분리한다.

| 시나리오 | 관찰 항목 | 통과 기준 |
| --- | --- | --- |
| 정상 업데이트 | 확인 → 다운로드 → 재시작 설치 → 버전 변경 | 상태 UI가 순서대로 바뀌고 재실행 후 기대 버전 표시 |
| 네트워크 실패 | 확인 또는 다운로드 중 연결 실패 | 오류 원인이 노출되고 재시도가 가능하며 작업 데이터 손실 없음 |
| 다운로드 중단 | 앱 종료·재실행 또는 취소 가능한 경계 | 손상된 installer를 실행하지 않고 다음 확인에서 안전하게 회복 |
| 업데이트 없음 | 최신 stable 설치본 | 사용자 행동 없이 비침습적 최신 상태 유지 |
| macOS 제한 | 서명·공증 전 패키지 | 자동 설치를 주장하지 않고 수동 설치 안내가 유지됨 |

같은 날 스트림 D는 현재 P1 구현을 코드·테스트 계약에 대조한다. `projectSessions`, `projectRevision`, `projectSaveTransaction`, `projectRecovery`, `projectProtection`, `electron/main.ts`를 각각 백로그 완료 기준과 매핑한다. 알려진 구현이 있다면 다시 만들지 않고 다음 표처럼 실제 실행 공백만 이슈로 분리한다.

| P1 항목 | 이번 주 확인 대상 | 후속 조건 |
| --- | --- | --- |
| P1-01 | single-instance lock, second-instance focus, 세션별 queue, dispose/zeroization | Windows에서 실제 두 번째 실행과 종료 후 재시작을 관찰 |
| P1-02 | stale base revision rebase, 충돌 path, 최신 DTO의 `REVISION_CONFLICT` | OCR·인페인팅 완료가 늦게 도착하는 현실적 test fixture 추가 여부 결정 |
| P1-03 | candidate, backup, 최종 재검증, Save As·rekey | Windows rename/file lock와 `.bak` 복구를 실파일로 검증 |

### Day 4 — Windows 실증과 브랜딩 패키지

Day 4는 기존 단위 테스트가 대신할 수 없는 실제 OS 동작에 집중한다. Windows 환경에서 두 번째 앱 실행 시 새 창 대신 기존 창이 복원·포커스되는지 확인한다. 또한 사용 중인 `.ctp` 파일, candidate, backup 상태를 각각 주입해 원자 저장이 기존 유효 파일을 보존하는지 확인한다. 테스트는 사용자 프로젝트가 아닌 임시 fixture에서 실행하고, 결과·명령·Windows 버전을 기록한다.

스트림 E는 브랜드 원본이 승인된 경우 아이콘 소스와 플랫폼 파생물을 만든다. Windows `.ico`, macOS `.icns`, Linux PNG 계층을 하나의 승인 원본에서 생성하고, electron-builder의 아이콘·Linux category·About 정보를 설정한다. 브랜드 자산이 아직 승인되지 않았다면 이 날에는 구현 대신 asset brief와 패키지 전후 비교 기준만 확정한다.

| 수용 기준 | 확인 방법 |
| --- | --- |
| Windows 설치 파일에 브랜드 아이콘 표시 | 새 Windows VM 또는 샌드박스에서 설치 파일·시작 메뉴·창 아이콘 확인 |
| macOS DMG/앱 번들 아이콘 적용 | Finder·앱 번들에서 아이콘과 서명 상태 확인 |
| Linux 데스크톱 항목 정비 | `.desktop` 파일 category, 앱 이름, hicolor 아이콘 계층 확인 |
| 기능 회귀 없음 | 패키징·스모크 테스트 및 기존 UI 화면 확인 |

### Day 5 — 통합 검토와 다음 주 Go/No-Go

Day 5에는 각 스트림의 PR을 통합하지 않고도 완료 증거를 하나의 상태표로 모은다. 차단된 credential·법률 검토는 명시적으로 No-Go로 남기고, 코드·테스트·문서가 준비된 항목만 다음 주 병합 순서에 넣는다. 업데이트 시험 결과, provenance 파일 예시, Windows 실증 결과, 남은 P1 gap, 브랜드 승인 여부를 `v0.1.4` 마일스톤 노트에 기록한다.
