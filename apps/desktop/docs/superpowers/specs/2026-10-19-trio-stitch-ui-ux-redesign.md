# Trio 데스크톱 Stitch UI·UX 재설계

상태: 사용자의 전체 화면 구현 승인에 따라 10개 주요 화면과 앱 대화상자·작업대 보조 영역을 Stitch에서 재설계하고 Electron 소스·로컬 빌드에 반영했다. 실제 Electron에서 작업 과제 18개·화면 측정 240회를 통과했으며 최종 독립 architect 검토에서도 추가 완료 차단 결함이 없음을 확인했다. 아래 1차 작업대 기록은 당시 범위와 검증 한계를 보존한다. 자동 저장·프로젝트 전체 되돌리기·수정 이력은 별도 저장·복구 설계가 필요한 미구현 요구사항이다.

## 사용자와 확인한 목적

- 대상은 별도 웹서비스가 아닌 Trio Electron 데스크톱 앱이다(Q1).
- 기존 시안의 부분 수정에서 벗어나 화면 배치와 조작 흐름을 함께 새로 설계한다.
- 기본 동선은 여러 페이지를 일괄 처리한 뒤 전체 진행을 보고 문제 있는 부분부터 검수하는 흐름이다(Q2).
- 좋은 디자인은 원하는 결과까지 자연스럽고 편안하게 도달하게 하는 디자인이다. 만화가 주인공이고 인터페이스는 조연이어야 한다(Q3).
- 처음 쓰는 사람에게는 쉬우며, 반복해서 쓰는 사람에게는 정교한 편집을 빠르게 제공한다.
- 명확함·집중·통제·신뢰·일관성을 우선한다. 사용자가 수정한 결과를 AI 재실행으로 잃지 않는 경험을 중요하게 다룬다.
- 프로젝트의 이슈 관리 위치는 `ksaeil2001/trio`의 GitHub Issues로 정했다(Q4). 기본 5개 라벨과 로컬 설정 초안을 승인했고 `docs/agents/` 문서 3개와 `AGENTS.md` 연결을 반영했다(Q7). 원격 라벨 생성은 이 승인에 포함되지 않는다.
- 자동 저장·프로젝트 전체 되돌리기·수정 이력은 새 UX의 필수 요구사항으로 설계한다(Q5). 현재 구현된 기능처럼 취급하지 않고, 실제 구현 범위와 저장·복구 계약은 시안 선택 뒤 검토한다.
- 첫 비교 과제와 이미지 직접 선택·검수 목록 선택의 두 시안을 확인했다(Q6).
- 대사를 수정한 뒤 `다음 항목`은 검수 상태를 유지하고 이동만 한다. 자동 저장은 수정 내용을 보존하며, `검수 확정`은 별도의 명시적인 사용자 행동으로 분리한다(Q8). 이 규칙을 A/B 양쪽에 동일하게 적용한다.
- 확인 필요 항목을 먼저 처리한 뒤 전체 페이지를 순서대로 읽으며 최종 확인하는 흐름을 권장한다(Q9). `확인 필요 0개`와 전체 페이지의 읽기 검수 완료를 구분한다. 이 선택으로 기존 내보내기 조건을 추가 제한하지 않는다.
- 다음 시안을 발전시킬 잠정 방향은 A의 캔버스 중심 배치다. 만화에서 직접 선택하고, 확인 목록은 필요할 때 펼친다(Q10). 두 선택·탐색 방식은 유지한다. 이 선호를 최종 제품 배치 승인이나 UX 과제 통과로 기록하지 않는다.

| 미검수·부분 실패 | 검수 완료 자체를 전체 출력 차단 조건으로 삼지 않는다. 승인 자산·품질 검사·식자 준비 조건을 적용하며 일부 내보내기와 실패 보고를 지원한다(`approvedCleanedAsset.ts:29`, `projectImageExport.ts:159`). | 내보내기 가능과 검수 완료를 같은 상태로 표현하지 않는다. 전체·일부·실패와 제외된 페이지·결과 종류·이유를 확인하게 한다. 새 일괄 승인이나 필수 전체 검수 게이트를 임의로 만들지 않는다. |

## 첫 시안의 제안 범위

최종 작업대의 중심은 다중 페이지 일괄 처리와 검수다. 첫 시안은 여러 페이지가 있는 프로젝트에서 한 페이지의 문제를 수정하고 저장·내보내기로 이어지는 작은 완결 흐름으로 검증한다. 한 장짜리 제품으로 범위를 축소하지 않는다.

1. 시작: 새 번역 프로젝트와 최근 작업에서 작업을 시작한다.
2. 이미지 추가: 파일·순서·기본 언어·실행 범위를 확인하고 처리한다. 모델·API·세부 옵션은 고급 설정에서 찾을 수 있게 한다. 실행에 필요한 준비가 빠졌으면 시작 동선에서 이유와 준비 화면으로 가는 행동을 제시한다.
3. 처리 중: 전체·페이지 진행과 현재 필요한 행동을 이해하고, 실제 지원되는 제어를 사용한다.
4. 검수·수정: 페이지나 검수 항목을 선택하고 큰 이미지에서 위치를 확인한 뒤, 해당 원문·번역·식자를 수정한다. 다음 페이지나 검수 항목으로 이동한 뒤에도 편집 문맥과 남은 확인 필요 대사 수를 이해할 수 있는지 확인한다. 문제 항목 처리 뒤 전체 페이지 읽기를 권장하며, 이 단계에서는 편집 패널을 접어 이미지를 중심으로 본다. 확인 필요 대사 수를 전체 페이지 품질의 검수율로 표시하지 않는다.
5. 저장·내보내기: 프로젝트 저장과 결과 이미지 내보내기를 구분하고 적용 범위·실패·결과 위치를 확인한다.

검수 화면은 같은 가상 작품·페이지·대사를 사용해 두 조작 흐름을 비교한다. 하나는 이미지의 영역을 직접 선택해 수정하는 흐름, 다른 하나는 검수 목록에서 항목을 골라 해당 이미지 위치로 이동하는 흐름이다. 두 진입은 모두 유지하고 패널의 최종 위치와 상시 노출 여부는 시안에서 비교한 뒤 결정한다. 검수 대사, 처리 실패, 사용자 확인 대기와 내보내기 불가 사유는 출처와 필요한 행동을 구분한다.

## 시각 탐색 방향

사용자가 제시한 `Editorial Workbench`를 콘텐츠 중심의 절제된 전문 편집기로 해석한다. 시작 화면의 따뜻한 오프화이트, 작업대의 차콜 다크, 절제된 파란 강조색을 탐색한다. 가독성·이미지 공간·일관성을 기준으로 판단하고, 화면별 밝기 차이와 기존 테마 선택의 관계는 최종 시각 규칙 전에 확인한다.

선택한 대사와 관련된 편집 항목을 보여주며, 현재 상태·저장 여부·실패 원인·필수 다음 행동은 숨기지 않는다. 세부 기능을 접더라도 해당 기능의 존재와 접근 방법을 알 수 있어야 한다.

## UI 평가와 UX 평가

| 축 | 평가 내용 | 남길 근거 |
| --- | --- | --- |
| UI | 이미지가 주 시각 영역인지, 한글·일본어·영문의 가독성, 정보 위계, 밀도, 컨트롤·상태의 일관성 | 각 시안과 대표 상태의 캡처, 문제 위치와 심각도 |
| 접근성 | 일반 텍스트 대비 4.5:1 목표, 키보드 이동·포커스, 조작 영역, 상태의 텍스트 설명 | 시각 시안의 대비 확인과 실제 프로토타입에서 가능한 조작 검증을 구분 |
| UX | 설명 없이 시작·다음 행동·처리 범위·현재 페이지를 이해하는지, 반복 수정이 자연스러운지 | 같은 과제에서 성공 여부, 도움을 요청한 지점, 행동 수와 길을 잃은 지점 |
| 신뢰·통제 | 처리 중단·실패와 사용자 확인을 이해하는지, 수정한 값·저장 상태·다시 실행할 범위를 이해하는지 | 상태별 과제와 관찰 기록, 지원되지 않는 기능의 별도 요구사항 |

참고 기준: [Nielsen Norman Group의 사용성 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/), [WCAG 2.2](https://www.w3.org/TR/WCAG22/). 참고 기준에 근거한 평가와 실제 사용자 관찰을 구분한다.

첫 과제는 ‘프로젝트 시작 → 여러 이미지 추가·일괄 처리 → 검수 항목이나 페이지 찾기 → 한 대사 수정 → 다음 페이지 검수로 이동 → 남은 상태 확인 → 전체 페이지 최종 읽기 → 프로젝트 저장 → 결과 내보내기’다. 정상 흐름 외에 준비 누락, 부분 실패, 재시도, 취소, 미저장 변경, 사용자 수정 후 재실행을 확인한다. 첫 과제의 성공을 전체 일괄 검수 UX의 합격으로 확대하지 않는다. 전체 과제는 아직 수행하지 않았고, 아래의 가상 대사 편집·되돌리기 시험만 진행했다. 합격 결과나 실제 처리 성능을 기록하지 않는다.

| 마무리와 상태 | 문제 검수 후 전체 페이지 최종 읽기로 이동하고 필요하면 해당 대사의 편집으로 돌아온다. 저장·처리·검수·내보내기 준비의 상태를 구분하고, 저장 실패나 출력 제외 이유와 다음 행동을 이해할 수 있게 한다. |

## Stitch 작업과 증거의 범위

새 프로젝트에서 시안을 만들고, 프롬프트·프로젝트 링크·화면별 캡처·비교 결과를 이 문서에 연결한다. 시안에는 가상 작품과 대사 데이터를 사용한다. 기존 Stitch 프로젝트는 참고 자료로 취급한다.

첫 생성 프로젝트: [TRIO Manga Localizer UI](https://stitch.withgoogle.com/projects/3968773052468212420?pli=1). 생성 요청은 시작·이미지 추가·일괄 처리·직접 검수·목록 검수·저장/내보내기의 6개 화면, 동일한 가상 작품 12페이지, 1440×900 창 기준과 새 신뢰 기능을 포함한다. 첫 6개 화면을 생성했고 아래 평가로 수정본을 요청했다. 생성기의 자체 완료·대비 충족 설명을 검증 결과로 사용하지 않는다.

### 첫 생성본의 UI·UX 검토

실제 Stitch의 렌더링된 화면과 접근성 트리에서 확인한 내용이다. 사용자의 과제 수행 관찰이나 실제 Electron 기능 검증은 아니다.

| 발견한 문제 | 영향 | 수정 요청 |
| --- | --- | --- |
| `.trioproj`, 미확인 PSD·CBZ 가져오기, 임의 모델·GPU 성능·처리시간 정보 | 기존 저장 계약과 기능 범위를 다르게 전달하고 첫 사용자의 정보 부담을 늘림 | `.ctp`로 바로잡고 미확인 기능·성능 수치와 기술 상세를 기본 화면에서 제거 |

초기 요청과 후속 교정 요청의 원문은 위 Stitch 프로젝트의 대화에 있다. 교정 요청은 새 기능 확대가 아니라 합의한 6개 화면의 범위·계약·비교 가능성 정리에 해당한다. 수정본의 반영 여부와 실제 클릭 가능한 범위는 추가 확인한다.

### 첫 교정본·프로토타입에서 확인한 범위(7개 화면)

- 새 오프화이트 홈을 포함해 7개 화면이 있으며, 기존 어두운 홈도 남아 있다. Stitch에서 `TRIO Manga Localization Editor` 프로토타입을 생성했다. 최초 진입은 이전 어두운 홈으로 연결되어 교정 대상으로 남았다.
- A와 B 양쪽에서 전체 12페이지 중 4번째 페이지, 대사 7개·확인 필요 3개·선택 #02와 같은 번역문을 확인했다. A의 수정문 보존 토글 제거, B의 기본 수정문 보존 안내와 75% 분기 설명도 확인했다. 모든 화면의 계약 준수나 상태 전이를 검증한 것은 아니다.
- 실제 만화는 A가 요리사와 아래 두 컷으로 구성된 페이지, B가 식당 바깥 장면으로 달랐다. 동일 원고라는 비교 조건은 아직 충족하지 못했다. 같은 A 원고를 B에 복제하고 목록 밀도를 낮추는 후속 요청을 제출했다.
- A의 공식 상세 패널 크기는 1280×1049, B의 데스크톱 프로토타입 문서 뷰포트는 1280×1024였다. 바닥글의 `1440x900` 문구는 실제 크기 검증의 근거가 아니다. 실제 레이아웃 기준과 잘림은 추가 확인이 필요하다. 시험한 모바일 보기 전환은 데스크톱으로 복원했다.
- 일부 기술 바닥글, 엔진 표기, 정적인 저장·되돌리기 표현이 남았다. 새 UX 필수 요구사항이 충분히 구체화됐거나 실제로 구현됐다고 판정하지 않는다.
- ZIP 내보내기와 공식 단일 화면 Download에서 다운로드 완료 이벤트를 확인하지 못했다. 대응 로컬 산출물 확보도 미확인이다. 타임아웃만으로 서버 측 생성 실패를 확정하지 않는다.
- 캡처 보관을 위한 별도 `data:` 이미지 URL 열기는 브라우저의 http/https 전용 URL 보안 정책에 의해 차단됐다. 이 경로는 중단했고 우회하지 않는다. 실제 확보하지 못한 PNG·ZIP 경로나 캡처를 산출물로 기재하지 않는다.

첫 교정 시점에는 시안 생성·일부 UI 교정·전문가 관점의 초기 흐름 검토까지 진행했다. 같은 과제에 따른 두 시안 UX 비교, 접근성 충족, 실제 Electron 동작과 번역 품질은 미검증이다. 최종 UX 선택은 비교 조건과 필요한 조작 검증을 마친 화면을 근거로 받는다.

### 후속 교정과 가상 조작 시험(Q8 이전)

동일 원고 복제·1440×900 실제 배치·프레임 이름·기본 조작·새 홈에서 시작하기를 명시해 후속 교정을 요청했다. 기존 7개 화면에 검수 화면 2개가 추가돼 총 9개가 됐다. Stitch의 완료 설명과 실제 표시 결과를 대조했으며, 아래 확인을 이유로 A/B 최종 선택을 보류한다. 자연어 생성 요청만 반복해 비교 완료로 간주하지 않는다.

최신 화면의 공식 미리보기는 [검수 A · 이미지 직접 선택](https://stitch.withgoogle.com/preview/3968773052468212420?node-id=02030bfefcc34c089ec10ee09809596d), [검수 B · 확인 목록 선택](https://stitch.withgoogle.com/preview/3968773052468212420?node-id=741875a15a6149b189c0a69c3b64c44f)다. 이 이름은 문서의 구분이며, Stitch 프레임의 실제 메타데이터는 아직 `Generating Screen...`으로 표시된다.

| 확인 | 실제 관찰 | 판정과 다음 조건 |
| --- | --- | --- |
| 원고·정보 밀도 | A는 요리사와 아래 두 컷, B는 식당 바깥 남자와 아래 두 컷으로 원고가 다르다. B의 검수 목록은 요약·이유 위주로 줄었다. | 목록 밀도 교정은 일부 반영됐다. 동일 이미지·말풍선·배율의 비교 조건은 불충족이다. |
| 실제 배치 | A 문서 뷰포트 1280×900, 내용 1440×901. B 뷰포트 1280×1049, 내용 1440×1049. 공식 데스크톱 미리보기에서 양쪽 우측 편집기와 하단 행동 일부가 잘렸다. | 내용 폭을 1440으로 쓰는 것만으로 대표 창 기준 충족을 주장하지 않는다. 동일 뷰포트에서 주요 행동이 보여야 한다. |
| 가상 대사 편집 | A의 사용자 번역 입력값을 바꿀 수 있었고 저장 중·저장됨 표시 변화를 확인했다. | 시안 내부의 가상 반응만 확인했다. 실제 자동 저장·복구 증거가 아니다. |
| 다음 검수 항목 | 포인터 입력은 도구의 소수점 iframe 좌표 검사로 수행되지 않았다. 같은 버튼에 키보드 Enter로 접근했지만 선택 #02·확인 필요 3개 중 1개 선택 표시가 그대로였다. | 항목 이동 성공은 미확인이다. 단순 이동과 검수 확정의 의미·각 상태 변화를 별도로 명확히 해야 한다. |
| 되돌리기 | 시작 사용자 문구 `오늘은 조금 일찍 집에 가자.`를 수정한 후 되돌리기를 실행했으나 AI 문구 `오늘은 조금 일찍 돌아가자.`로 바뀌었다. 시험 뒤 예시 사용자 문구를 원래대로 복원했다. | 실제 사용자 편집 이력을 복원하는 동작을 충족하지 못했다. 시안의 되돌리기를 신뢰 기능 검증으로 채택하지 않는다. |
| 시작 화면·메타데이터 | 새 화면의 실제 이름은 바뀌지 않았다. 기존 프로토타입은 7개 화면으로 생성된 버전이며, 이후 새 홈 시작 및 최신 9개 화면의 전체 연결은 검증하지 않았다. | 생성기의 완료 설명만으로 연결 변경을 확정하지 않는다. 최종 과제 수행 전에 확인한다. |

가상 프로토타입에서 AI 호출·실제 파일 저장·사용자 원고 업로드는 수행하지 않았다. 실제 제품 결함을 확인한 결과가 아니라, 생성된 시안이 합의한 신뢰 경험을 표현하는지 시험한 결과다. 미리보기의 항목 이동·되돌리기 문제는 시안의 수용 조건으로 남기며, 제품 코드의 문제로 옮겨 적지 않는다.

사용자 Q8 답변으로 다음 상태 전이를 합의했다. 자동 저장·다음 항목 이동·검수 완료를 같은 행동으로 묶지 않는다. 생성된 시안에 이 규칙을 적용하고 실제 표시·가상 조작 결과로 반영 여부를 구분한다.

| 행동 | 편집 내용 | 검수 상태와 남은 수 |
| --- | --- | --- |
| 번역문 수정·자동 저장 | 사용자 수정값을 보존하고 저장 중·저장됨·실패를 표시 | 저장을 이유로 검수 확정하지 않으며, 남은 확인 필요 수를 자동으로 줄이지 않는다. |
| 다음 항목·다음 페이지 | 수정값과 편집 문맥을 보존하고 대상으로 이동 | 이동 자체로 검수 확정하지 않는다. 남은 수는 그대로다. |
| 검수 확정 | 사용자가 확인한 대상과 현재 수정값을 명시적으로 확정 | 해당 대상의 검수 상태·남은 수를 갱신한다. 이후 이동은 별도 행동으로 제공한다. 검수 항목이 0개라고 전체 페이지의 모든 품질이 검수된 것으로 표시하지 않는다. |

이 합의는 조작과 검수 상태의 의미에 관한 것이다. 자동 저장의 실제 복구 범위, 프로젝트 전체 되돌리기 구현 및 저장·복구 계약 변경의 승인을 포함하지 않는다.

Q9로 마무리 흐름을 `문제 항목 우선 검수 → 전체 페이지 최종 읽기(권장) → 저장·내보내기`로 확인했다. 읽기 화면은 현재 페이지·이전/다음·편집으로 돌아가기·원본 비교에 집중한다. 읽기 진입이나 마지막 페이지 열람만으로 품질 확인을 자동 확정하지 않는다. 문제 항목이 남거나 최종 읽기 전이라도 기존 출력 준비 조건에 따른 내보내기를 임의로 막지 않는다.

Q8 이후 최신 A/B 두 기존 화면을 대상으로 상태 규칙 교정을 요청했다. 화면 수는 9개로 유지됐고, 실제 렌더링에서 A의 `검수 확정 (Enter)`·`다음 대사 이동 (F3)`·이전/다음, B의 `검수 확정`·`다음 항목`이 분리된 것을 확인했다. 이동 시 수정문 보존과 확정 시에만 남은 수를 갱신한다는 설명도 추가됐다.

이 교정 뒤의 기능 시험은 완료하지 못했다. A의 다음 버튼 Enter 및 F3 입력은 브라우저 조작 도구의 입력 대기 시간 초과로 수행 성공이 확인되지 않았다. B의 다음 버튼은 실제 뷰포트 폭 1280에서 x=1283 부근부터 배치돼 화면 밖에 있다. 문구·버튼 분리를 상태 전이·수정문 보존의 작동 검증으로 확대하지 않는다. 시험에 쓴 A의 문구는 원래 사용자 문구로 복원했다. Q8 이전에 발견한 되돌리기 문제도 교정 후 해결됐다는 근거가 없다.

공식 `View Code`에서 원고·배치를 직접 정리할 수 있는지 확인했지만 코드 입력은 읽기 전용이었다. 승인 없이 다른 제품 코드로 옮겨 구현하지 않는다. 이 시점의 미해결 조건이었던 원고·창 조건·주요 조작 노출은 아래 후속 교정에서 각각 다시 확인했다.

### Q9 이후 최종 읽기 시안

최종 읽기 화면을 추가하고 기술 표기·상태 범위를 정리한 수정본을 요청했다. 이 과정에서 읽기 화면 2개가 추가돼 총 11개가 됐다. 수정본의 실제 문서 뷰포트 1280×900, 내용 1280×901을 확인했다. 가로 넘침은 없지만 1px의 세로 넘침과 하단 상태의 중복 표기는 남았다.

최신 공식 미리보기: [최종 읽기 · 페이지 순서 검수](https://stitch.withgoogle.com/preview/3968773052468212420?node-id=e5e56ec518e14a7cbcc1dfa2f76ec72f).

- 최신 읽기 화면은 A에서 사용한 9개 이미지의 `src` 배열과 동일하다. 원고를 새로 생성했다는 설명 대신 실제 이미지 자산 일치로 확인했다. 이 사실을 B의 동일 원고 교정에 활용해 실제 세 원고 이미지 URL을 지정하는 후속 요청을 제출했다.
- 읽기 화면은 우측 패널이 접힌 상태이며 이전/다음 페이지·원본 비교·확대/맞춤·편집 복귀·저장/내보내기 컨트롤이 있다. A/B 양쪽에도 `전체 페이지 최종 읽기` 접근 행동이 추가된 것을 확인했다. 실제 화면 간 연결과 페이지 이동 성공까지 확인한 것은 아니다.
- 최신 읽기 화면에서 프로젝트 확인 필요 대사 0개와 최종 읽기 진행 중을 별도로 표시한다. 이전의 페이지 한정 0개 표기도 남아 있어 중복을 정리해야 한다. 이 화면은 문제 항목 처리 뒤의 가상 상태이며 실제 프로젝트 품질 합격을 나타내지 않는다.
- `BLEED 3mm`, `TRIO-ENG-RENDER-PASS`, 선택 대사·원문 디버그 오버레이는 최신 읽기 화면에서 제거됐고 `자동 동기화`는 `자동 저장`으로 바뀌었다. 사용자가 읽는 만화와 관련된 정보에 집중하는 방향의 일부 UI 교정이다.

### 실제 자산을 지정한 A/B 교정

최신 읽기 화면이 A의 이미지 자산을 그대로 재사용한 사실을 근거로, A의 세 원고 이미지 `src`를 명시해 B 교정을 요청했다. 이 교정은 같은 추상적 원고 복제 요청의 반복과 구분한다. 실제 A/B 모두 같은 상단 요리사·하단 거리·하단 인물의 세 자산을 사용하는 것을 확인했다. 두 화면에서 기술·디버그 문구도 제거됐다. 원고 문제는 이 범위에서 해결됐지만 말풍선 배치·크롭·배율까지 같다는 검증은 별도다.

A와 B의 문서 내용 폭은 모두 1280으로 정리됐고, 검수 확정·다음 항목 버튼이 x0~1280 안에 들어왔다. A의 문서 뷰포트·내용은 1280×900/1280×901이다. B는 뷰포트·내용이 1280×1049/1280×1049이고 main의 `min-h-[1024px]` 때문에 footer가 y1024 아래에 남았다. B의 세 원고 박스도 A와 크기가 달라, 확인한 클래스와 실제 원고 박스 크기를 명시해 B의 고정 높이·배율만 후속 교정 요청했다. 새 기능이나 실제 저장·AI 실행을 추가하는 요청은 아니다.

후속 교정에서 B main의 최소 높이를 0으로 바꾸고 뷰포트에 맞추도록 했다. A/B를 같은 공식 데스크톱 미리보기 1280×1024에서 다시 확인했다. A의 내용은 1280×1025이고 검수 확정·다음 항목은 y935 부근, B의 내용은 1280×884이고 두 버튼은 y744 부근, footer는 y858 부근이었다. 두 안의 주요 행동이 이 공통 창 안에 있음을 확인했으며, 이를 1280×900·1440×900 충족 근거로 확대하지 않는다. B의 최종 원고 박스 크기·크롭과 대표 창 두 크기는 추가 확인 대상이다.

같은 미리보기에서 가상 문구를 수정하고 표시된 다음 항목 단축키·접근성 대상에 키보드 입력을 보냈으나 #02에서 이동 성공은 확인하지 못했다. 도구 입력 제한과 시안의 연결 문제를 구분하기 어려우므로 버튼 고장으로 단정하지 않는다. 시험 문구는 원래 사용자 문구로 복원했다.

### 실제 글자 크기·대표 문구 대비 점검

가독성 검토에서 두 검수안의 번역 입력 13px와 보조 문구 9~11px를 확인했다. B의 단축키 안내는 전경 `rgb(66,71,84)`, 배경 `rgb(24,28,34)`로 계산 대비 약 1.84:1이었다. 해당 영역에 배경 이미지가 없음을 확인하고 렌더링된 전경·조상 배경색으로 계산했다.

교정 뒤 두 안의 번역 입력은 14px·줄높이 22px가 됐다. A 편집 패널에서 조사한 한국어 보조 문구는 12px 미만이 없었고, B 단축키 안내는 12px와 전경 `rgb(194,198,214)`로 바뀌어 같은 배경에서 약 10.05:1이었다. 대표 문구 한 곳의 개선이며 전체 화면의 대비·접근성 충족은 아니다. B의 글자 수·수정문 보존 설명·일부 식자 라벨에는 10~11px가 남아 후속 정리가 필요하다.

이 수치는 Stitch 프로젝트의 작업 캔버스에서 확인한 값이다. 이후 공식 A 미리보기를 다시 불러오고 같은 공식 메뉴로 새 탭도 열어 대조했으나, 별도 미리보기의 입력은 이전 13px였다. 캔버스 textarea의 class는 `text-[14px] leading-[22px]`, 별도 미리보기는 이전 `font-body-md text-body-md leading-relaxed`로 내용 차이가 있었다. 원인이나 서버 저장·동기화 완료는 확인하지 못했다. 따라서 위 글자 교정을 독립 미리보기에도 반영·저장 완료됐다고 보고하지 않는다. 최신 교정 확인은 프로젝트 작업 캔버스를 기준으로 하고, 미리보기 링크는 배치 초안 참조로 구분한다. 임의 URL 변경이나 비공식 API로 우회하지 않는다.

### 현재 설계 방향과 남은 검증

Q10으로 A를 발전 방향으로 정했다. 기본 캔버스와 선택 대사 편집을 중심으로 두고, 확인 목록은 요청할 때 펼치는 경험을 구체화한다. 전체 페이지 읽기는 두 진입 방식의 공통 마무리 단계다. 기존 B를 삭제하거나 접근 방식을 제거하지 않는다.

현재 확인한 것은 설계 기반 합의, 로컬 설정 적용, 동일 원고 자산과 일부 배치·가독성의 교정이다. 다음 검증은 A 방향에서 `#02 수정 → 확인 목록 또는 #03 이동 → 원래 항목 복귀 → 되돌리기·다시 실행`을 대표 창 크기와 함께 확인하는 것이다. 실제 저장·복구와 프로젝트 전체 이력 구현은 이 시안의 가상 반응과 별개다.

Stitch의 시각 시안, 클릭 가능한 조작 검증, 실제 Electron 기능 검증은 서로 다른 근거다. 디자인 프로토타입의 실행 성공을 OCR·번역·원문 제거·식자 품질 개선으로 보고하지 않는다. 제품 코드 반영과 핵심 승인 흐름 변경은 구체적인 설계·영향을 검토하고 사용자 승인을 받은 뒤 다룬다.

## Electron 작업대 1차 반영과 제품 검증

2026-10-19 사용자의 후속 구현 승인으로 renderer의 레이아웃과 기존 동작 연결을 변경했다. 새 기본값은 112px 페이지 레일·320px 선택 편집기·하단 결과 닫힘이다. 저장된 사용자의 패널 선호는 유지한다. 페이지 탐색을 레일 위쪽에 두고 자료 추가는 아래에 배치하며, 프로젝트 제목·수동 저장 상태·프로젝트 확인 필요 수를 표시한다. 좌표가 있는 대사는 이미지 위에서 직접 선택하고 기존 확인 목록도 선택적으로 열 수 있다. 좌표가 없는 대사에 임의 위치를 만들지는 않는다.

번역문 입력·저장·이동은 검수 확정과 분리했다. 미확정 번역은 확인 필요 목록에 남고, 명시적 확정은 선택 대사에 머문다. 늦은 확정 응답이 다음 선택과 초안을 덮어쓰지 않게 했다. 최종 읽기는 편집기를 `hidden`·`inert`로 숨기되 마운트를 유지하고, 페이지 왕복 후 선택·초안과 원래 패널 선호를 보존한다. 페이지 목록 버튼과 `Ctrl+B`는 같은 임시 읽기 상태를 조작한다. 읽기 진입·페이지 이동만으로 품질 합격이나 검수 완료를 표시하지 않는다.

## 독립 검토 반영

2026-10-19 architect 검토에서 기존 고정 배치나 자동 승인을 강제하는 위반은 찾지 못했다. 검수 목록의 출처·미검수 의미, 다음 페이지로 검수 이어가기, 첫 실행의 필수 준비 안내, 로컬 설정 승인과 원격 라벨 생성 권한의 구분을 보완했다. 기능 지원 범위는 별도 explorer의 코드 조사 결과와 메인 에이전트의 핵심 경로 확인을 반영했다.

후속 architect 검토에서 동일 원고·창 조건 미충족과 시안의 되돌리기 실패를 높은 우선순위의 미해결 조건으로 확인했다. 비교 완료로 포장하거나 같은 자연어 교정 요청만 반복하지 않고, 이동과 확정의 의미를 먼저 질문하라는 검토를 반영해 Q8을 확인했다. 검토는 문서와 메인 에이전트의 관찰 기록을 근거로 한 읽기 전용 검토이며 독립 브라우저 재실행 증거는 아니다.

최종 단계의 architect 검토에서는 동일 원고 교정 뒤 잠정 배치 선호를 질문할 수 있지만 최종 기본 배치 승인이나 UX 과제 통과로 기록해서는 안 된다고 판단했다. 공통 1280×1024 확인을 최소 1280×900 합격으로 확대하지 않고, 크롭·배율·조작·글자 교정의 실제 확인 범위를 각각 남기라는 지적을 반영했다. 이후 확인한 글자 크기와 대표 문구 대비 결과는 메인 에이전트의 추가 관찰이며 독립 검토자가 브라우저에서 재실행한 결과가 아니다.

Electron 구현 후 독립 architect 검토에서 좁은 창의 상단 확인 목록 토글, 읽기 중 페이지 목록을 열 때 편집기 마운트가 사라지는 경로, `Ctrl+B`가 실제 표시 대신 저장된 선호만 변경하는 경로를 지적했다. 공통 Shell 조작 경로와 임시 읽기 상태로 수정하고 1100px·900px 회귀 및 실제 Electron 과제에 반영했다. 재검토에서 지정 범위의 완료 차단 결함이 없고 실행 결과·정상 종료·소스/빌드 해시 일치를 확인했다. 마지막 미사용 import 제거 후에도 같은 Electron 과제를 재실행해 검증 산출물을 최종 파일과 맞췄다. 독립 검토자가 실제 AI 처리나 설치 프로그램을 실행한 검증은 아니다.


## 전체 화면 후속 반영과 검증

사용자의 “남은 모든 화면과 대화상자까지” 구현 승인으로 홈·프로젝트·파일·AI 준비·편집 도구·사전·설정·새 프로젝트·환경 준비·캔버스 작업대의 10개 화면을 연결했다. 관리 화면은 공통 탐색/위치·목록/상세, 생성은 이미지 순서 보드, 설정은 범주와 저장 영역, 작업대는 캔버스 중심 구조를 사용한다. 캐릭터/용어 편집·추출 승인, 배치, 안내/도구 대상, 설정 이탈, 프로젝트 확인·암호·호환 경로 입력도 새 앱 dialog와 목적별 구조로 정리했다. 원시 native confirm/prompt는 사용하지 않는다.
