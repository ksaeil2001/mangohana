# v0.1.4 Release Hygiene PR 가이드

> **목적:** 다음 릴리스 전에 production dependency advisory, Linux package category, Release asset allowlist, packaging asset CI trigger를 작고 검증 가능한 PR로 처리한다.
> **비범위:** Trio icon 원본 확정, `appId` migration, public updater enable, unsigned stable tag 허용은 이 PR에 포함하지 않는다.

## 1. 이 PR의 변경 범위

| 파일 | 변경 | 이유 |
| --- | --- | --- |
| `package-lock.json` | `js-yaml` `4.3.0` → `4.3.1` | production audit의 high advisory 제거 |
| `package.json` | `build.linux.category: "Graphics"` | Linux desktop metadata를 확정된 제품 category에 맞춤 |
| `.github/workflows/package-release.yml` | `build/**` trigger, `latest*.yml`만 artifact allowlist | build asset 변경을 package CI에 포함하고 `builder-debug.yml` 공개 방지 |
| `.github/workflows/windows-package.yml` | `build/**` trigger | Windows package verification도 icon/installer asset 변경을 놓치지 않음 |
| `tests/ci/packageReleaseSigningGate.test.ts` | path filter·metadata allowlist 계약 test | workflow 편집의 release hygiene regression 방지 |

`productName`, artifact filename, `appId`는 이 PR에서 바꾸지 않는다. `appId`는 installed app identity 및 auto-update continuity에 영향을 줄 수 있으므로 public update delivery가 준비된 migration PR에서 별도로 다룬다. icon 원본도 아직 미정이므로 default Electron icon warning은 이 PR 뒤에도 의도적으로 남는다.

## 2. PR 전 점검과 기대 결과

| 명령 또는 검증 | 기대 결과 |
| --- | --- |
| `npm ci` | lockfile의 `js-yaml@4.3.1` 설치 |
| `npm audit --omit=dev --json` | `critical`, `high`, `moderate`, `low` 모두 0 |
| `npm run typecheck` | 통과 |
| `npm test` | 전체 test 통과; workflow contract test 2개 포함 |
| `npm run dist:linux` | 성공, `application Linux category is set to default "Utility"` warning 없음 |
| `npm run smoke:package` | packaged app startup 성공 |
| GitHub Release artifact 목록 | installer·DMG·ZIP·AppImage·`latest*.yml`만 포함; `builder-debug.yml` 제외 |

`npm ci`가 전체 dev dependency advisory를 별도로 출력할 수 있다. 이는 production audit 결과가 아니며, Vite/jsdom/electron-builder toolchain update를 다른 compatibility PR로 분리한다. `npm audit fix --force`는 Electron/Vite major upgrade를 암시할 수 있으므로 이 PR에서 실행하지 않는다.

## 3. GitHub workflow 반영 방법

현재 GitHub credential에는 `.github/workflows/`를 CLI로 push할 권한이 없으므로, workflow 두 파일은 **GitHub 웹 UI에서 같은 PR branch에 반영**해야 한다.

1. source `trio`에서 `chore/v014-release-hygiene` branch를 만듭니다.
2. `package.json`, `package-lock.json`, `tests/ci/packageReleaseSigningGate.test.ts` 변경을 branch에 올립니다.
3. GitHub의 **Code → Add file → Edit file**에서 `.github/workflows/package-release.yml`과 `.github/workflows/windows-package.yml`을 같은 branch로 편집합니다.
4. PR 설명에 아래 release evidence를 붙입니다. credential, PFX, API key, 실제 원고 및 전체 사용자 경로는 붙이지 않습니다.

```markdown
## Release hygiene evidence

- [ ] `npm ci` completed from committed lockfile
- [ ] `npm audit --omit=dev --json`: production high/critical/moderate/low = 0
- [ ] typecheck and full test passed
- [ ] Linux AppImage build passed; no default `Utility` category warning
- [ ] packaged-app smoke passed
- [ ] artifact allowlist contains only deliverable binaries and `latest*.yml`
- [ ] icon warning is expected until approved source artwork is supplied
```

## 4. Review 기준

release reviewer는 `release/*.yml` wildcard가 남아 있지 않은지, `latest.yml`, `latest-mac.yml`, `latest-linux.yml`을 각각 명시했는지 확인한다. `build/**` trigger는 icon이나 installer metadata가 들어갈 Electron Builder default directory를 포괄한다. 아직 icon file을 commit하지 않았으므로 icon path·format·copyright source를 임의로 추가하지 않는다.

## 5. 병합 뒤 확인

이 PR은 unsigned stable tag gate를 바꾸지 않는다. `main` package workflow가 성공하더라도 stable tag는 기존 policy에서 차단되어야 한다. GitHub Release asset allowlist가 실제 upload에 적용되는지는 다음 **signed stable delivery candidate**에서 확인해야 하며, 현재 historical `v0.1.3` asset을 소급 수정하는 작업은 별도 운영 결정이다.
