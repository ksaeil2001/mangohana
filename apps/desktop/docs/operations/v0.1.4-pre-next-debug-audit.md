## 3. 확인된 세부 근거

### 3.1 Linux package metadata와 아이콘

2026-08-18 local `npm run dist:linux`은 exit code 0으로 AppImage를 만들고 packaged smoke도 통과했다. 다만 electron-builder는 다음 두 warning을 냈다.

> `application Linux category is set to default "Utility"`  
> `default Electron icon is used`

사용자 확정 범위인 Linux `Graphics` category와 Trio 상용 표기가 packaged output에 반영되지 않았다는 직접 증거다. icon 원본은 아직 미정이므로 기본 Electron icon 자체는 release blocker로 남긴다. 반면 Linux category는 별도의 원본 asset이 필요하지 않아 P1-04 metadata 수정 후보로 분리한다.

### 3.2 Dependency audit

`npm audit --omit=dev`는 `js-yaml@4.3.0`에 high advisory 1건을 보고했다. 영향 범위는 `>=4.0.0 <4.3.1`이고 registry에는 `4.3.1`이 존재한다. root runtime dependency `electron-updater@6.8.9`와 packaging dependency chain의 선언은 모두 `^4.1.0`이므로, **lockfile을 4.3.1로 갱신하는 최소 수정**은 semver 범위 내다. `npm audit fix --dry-run`은 lockfile 변경을 자동 제안하지 않았으므로, 다음 수정 PR에서는 명시적 lockfile update 후 전체 test·package smoke·audit 재실행이 필요하다.

### 3.3 Public delivery 전환 미완료 경계

현재 `src/shared/autoUpdateStatus.ts`의 `TRIO_RELEASE_URL`과 `package.json` publish provider는 private `ksaeil2001/trio`를 가리킨다. public delivery repository를 실제로 enable하기 전에는 installer의 updater feed와 error UI의 “릴리스 보기”가 모두 private source Release를 향한다. 이 상태는 기존 private Release update 404 진단과 일치하며, `trio-releases`를 만들고 metadata를 publish하는 PR에서 configuration·URL·packaged update QA를 한 묶음으로 변경해야 한다.

### 3.4 CI trigger coverage

`package-release.yml`과 `windows-package.yml`은 `package.json` 변경에는 반응하지만, build icon 또는 installer asset만 바뀌는 상황을 포괄하는 asset directory path를 명시하지 않는다. icon을 package config와 함께 최초 추가하면 `package.json` 변경이 있어 우연히 trigger되지만, 이후 icon 교체 같은 asset-only 변경은 자동 package test를 건너뛸 수 있다. P1-04 metadata PR에서 실제 asset directory를 확정한 뒤 두 workflow의 path filter와 정적 workflow contract test를 같이 갱신한다.

### 3.5 Updater release URL·historical Release asset hygiene

`AutoUpdateStatusControl`은 update error일 때도 “릴리스 보기”를 보여 주지만, `TRIO_RELEASE_URL`은 private source repository의 `releases/latest`을 가리킨다. controller test는 download/install/error 상태를 잘 다루지만 `shell.openExternal()`이 이 URL을 여는지와 public delivery 전환 뒤 private URL이 사라지는지는 test하지 않는다.

현재 `v0.1.3` GitHub Release에는 installer·AppImage·DMG·ZIP과 `latest.yml`, `latest-mac.yml`, `latest-linux.yml`이 있으며 latest Release로 표시된다. 이 historical release는 current signing governance가 도입되기 전에 만들어졌으므로, 새 stable workflow가 차단된다는 사실만으로 기존 asset의 운영 의미가 자동으로 바뀌지는 않는다. cloud signing·public delivery가 준비될 때 기존 release를 legacy로 표시할지의 release owner 결정을 남긴다.

또한 current workflow의 artifact pattern은 모든 `release/*.yml`을 받아 GitHub Release에 올린다. `builder-debug.yml`에는 secret은 확인되지 않았지만 builder file pattern 등 내부 build diagnostics가 들어 있고 updater에는 필요 없다. future public delivery workflow에서는 `latest*.yml`만 allowlist하고, current private workflow도 같은 allowlist로 맞추는 것이 적절하다.

### 3.6 Electron hardening과 CI-only dependency audit

`electron/main.ts`은 `contextIsolation: true`, `nodeIntegration: false`, local-only dev server allowlist, restrictive CSP를 사용한다. renderer에서 `dangerouslySetInnerHTML` 계열의 직접 HTML 삽입도 발견되지 않았다. 반면 `sandbox: false`는 Electron의 renderer sandbox 기본값을 명시적으로 해제한다. Electron은 모든 renderer의 process sandboxing을 권장하며, sandboxed preload에서도 Trio가 쓰는 `contextBridge`, `ipcRenderer`, `webUtils`는 지원 범위에 포함한다.[1] 따라서 AUD-06은 즉시 변경이 아니라, current preload·custom image protocol·package smoke를 기준으로 `sandbox: true` 또는 `app.enableSandbox()` migration을 검증할 P2 hardening 항목이다.

전체 `npm audit`는 high 15, moderate 1을 보고했다. production runtime 범위는 `js-yaml@4.3.0` high 1건이고, 나머지는 Vite/PostCSS/nanoid, jsdom/undici, electron-builder/node-gyp/tar 등 development·CI toolchain 경로에 집중되어 있다. 특히 registry의 `js-yaml@4.3.1`은 current upstream `^4.1.0` 범위 안에 있으므로 first patch candidate다. dev/CI audit는 Electron/Vite/electron-builder upgrade와 lockfile update를 작은 PR로 나누어 packaged smoke까지 확인해야 하며, 무차별 `npm audit fix --force`를 적용하지 않는다.

`@electron/fuses`는 devDependency로 존재하지만 packaging hook 또는 fuse assertion source는 발견되지 않았다. fuse 변경은 Electron 업데이트·native packaging과 결합하므로 source/Windows/Linux packaging smoke를 포함하는 별도 security hardening PR에서만 검토한다.

## 4. 감사 결론과 다음 수정 순서

현재 source 기준으로 typecheck, 전체 test, production build, IPC/storage smoke, Linux AppImage build와 packaged startup smoke는 모두 통과했다. 따라서 이번 감사에서 발견한 항목은 “현재 앱이 전반적으로 실행되지 않는다”는 결함이 아니라, **다음 stable delivery 전에 고쳐야 할 release hygiene·dependency·branding·security hardening gap**이다.

| --- | --- | --- | --- | --- |
| P0 | public update delivery enable 전 gate | AUD-03, AUD-07, AUD-08 | `trio-releases` 전환 시 updater provider·release URL·openRelease test·installed Windows update QA를 한 PR/QA 묶음으로 처리 | packaged stable candidate가 public delivery metadata만 조회하고, private source URL이 test·runtime config에서 제거되며 signing gate를 우회하지 않음 |
| P1 | dependency remediation | AUD-02, AUD-10 | `js-yaml` 4.3.1 lockfile update를 첫 작은 PR로 분리. 이후 Vite/jsdom/electron-builder toolchain은 compatibility group별 업데이트 | production audit high 0, target package test/typecheck/build/package smoke 통과. dev/CI advisory는 각 residual의 owner·upgrade 계획 기록 |

### 권장 시작 순서

1. **AUD-02:** `js-yaml@4.3.1`으로 lockfile을 명시적으로 올리고 `npm audit --omit=dev`, full test, Windows/Linux package smoke를 재실행한다. 이 변경은 current upstream `^4.1.0` dependency range 안에 있다.
2. **AUD-01/AUD-04/AUD-05/AUD-09:** approved icon 원본이 없어도 Linux `Graphics` category, Trio package-facing text, metadata asset allowlist와 CI path tests를 먼저 분리한다. appId 변경은 updater identity에 영향을 줄 수 있으므로 별도 migration decision 없이는 수행하지 않는다.
3. **AUD-03/AUD-07/AUD-08:** GitHub App·protected environment·cloud signer가 실제 준비된 뒤에만 public delivery provider 전환과 existing v0.1.3 legacy treatment을 결정한다. 이 단계 이전에는 stable tag 차단을 유지한다.
4. **AUD-06/AUD-11:** sandbox/fuses는 function-preserving test가 선행되어야 하므로 feature release와 섞지 않는 dedicated hardening PR로 진행한다.

## 5. 감사의 한계

Windows 실제 설치·파일 잠금·업데이트 전환의 잔여 P1-01/P1-03 QA와 cloud signing은 local Linux sandbox에서 대체할 수 없다. GitHub Actions run 목록 API는 current CLI integration token에서 403이었으나, GitHub browser UI로 마지막 code commit `812749e`의 Windows package run #13과 multi-platform package-release run #17 성공을 확인했다. 이후 코드 변경은 새 package CI run과 Windows real-device QA를 다시 요구한다.

검증·재현이 끝나기 전에는 위 항목을 release code defect로 단정하지 않으며, 외부 signing/branding 결정이 필요한 blocker와 즉시 수정 가능한 코드·설정 결함을 구분한다.
