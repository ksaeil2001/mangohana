# Trio v0.1.4 candidate evidence

> 2026-09-17 범위 갱신: 이 문서의 macOS 항목은 **non-MVP / future scope**이며 현재 MVP 지원이나 Release Gate 요구가 아닙니다. Linux 범위는 변경하지 않습니다. [현재 플랫폼 정책](mvp-platform-scope.md)을 우선합니다.
> 이전 시점의 실행 결과와 gate 상태는 역사적 기록이며 현재 후보 판정은 [최신 Release Gate 보고서](../release/2026-09-17-mvp-release-gate.md)를 따릅니다.

이 문서는 공개 promotion 전에 private source workflow가 생성해야 하는
immutable candidate bundle의 파일 계약과 검증 방법을 정의한다. 이 문서와
`scripts/release-candidate-evidence.mjs`는 서명·공증·물리 장비 QA를 수행하지
않는다. 그런 결과는 별도 시스템에서 생성한 **sanitized summary**를 입력으로
받고, 하나라도 빠지거나 `false`이면 stable candidate를 거부한다.

## 실행 경계

스크립트는 Node.js built-in 모듈만 사용한다. assets 디렉터리는 한 단계의
regular file만 포함해야 하며, symlink·하위 디렉터리·glob·원격 URL·path
traversal을 허용하지 않는다. `release-evidence.json`은 source SHA와 package
version을 포함하지만 자기 자신의 digest는 포함하지 않는다. 자기 참조를
피하기 위해 `release-evidence.sha256`이 canonical evidence 파일의 promotion
digest 입력이 된다.

생성:

```powershell
Set-Location "C:\Users\ksaei\OneDrive\문서\trio-main"
node scripts/release-candidate-evidence.mjs create `
  --assets-dir .\candidate-assets `
  --source-sha <40-hex-source-sha> `
  --version 0.1.4 `
  --verification-file .\candidate-verification.json
```

재검증:

```powershell
Set-Location "C:\Users\ksaei\OneDrive\문서\trio-main"
node scripts/release-candidate-evidence.mjs verify `
  --assets-dir .\candidate-assets `
  --source-sha <same-40-hex-source-sha> `
  --version 0.1.4
```

`create`는 이미 존재하는 evidence JSON을 덮어쓰지 않는다. `verify`는
evidence JSON, sidecar, checksum, updater metadata와 실제 파일 bytes를 모두
다시 계산한다. 결과 JSON에는 비밀값·절대 경로·raw signing/notarization log가
포함되지 않는다.

이 verifier는 입력 디렉터리를 읽는 동안 발생하는 동시 writer나 hard-link를
workflow 수준에서 해결한다고 주장하지 않는다. Task 5B promotion은 candidate
artifact를 격리된 workspace에 한 번 복사·고정하고, candidate/source/evidence
digest를 기록한 뒤 공개 직전에 같은 immutable bundle에 대해 `verify`를 다시
실행해야 한다. 그 download/copy와 TOCTOU 경계는 이 Task 5A의 범위가 아니다.

## stable public asset allowlist

현재 package version을 `V`라고 할 때 assets 디렉터리에는 아래 파일만 둘 수
있다. macOS blockmap은 `Trio-V.dmg.blockmap` 또는 `Trio-V.zip.blockmap` 중
정확히 하나를 사용하고 `latest-mac.yml`이 그 파일을 명시적으로 참조해야
한다.

```text
Trio-Setup-V.exe
Trio-Setup-V.exe.blockmap
latest.yml
Trio-V.dmg
Trio-V.zip
Trio-V.(dmg|zip).blockmap       # 정확히 하나
latest-mac.yml
Trio-V.AppImage                 # Linux manual download; updater metadata 없음
SHA256SUMS
trio-V.cdx.json                 # CycloneDX JSON
THIRD_PARTY_NOTICES.md
RELEASE_NOTES.md
release-evidence.json
release-evidence.sha256
```

`latest.yml`은 Windows installer를, `latest-mac.yml`은 macOS DMG·ZIP·선택된
blockmap을 참조해야 한다. metadata의 `version`, filename, declared `size`와
base64 SHA-512는 실제 bytes와 일치해야 한다. parser는 필요한 scalar field만
읽으며, 일반 YAML evaluator를 사용하지 않는다. `latest-linux.yml`, 다른
blockmap, source archive, `.ctp`/project asset, `builder-debug.yml`, raw log,
PFX/PEM/key/token 파일은 모두 거부된다.

Linux는 v0.1.4에서 AppImage 수동 다운로드만 공개한다. `latest-linux.yml`과
Linux blockmap을 만들거나 공개하지 않으며, updater disabled 증거가 필요하다.

## checksums와 evidence

`SHA256SUMS`는 다음 형식의 canonical LF 파일이다.

```text
<lowercase sha256>  <basename>
```

basename 기준 오름차순이며, 자기 자신과 `release-evidence.json`,
`release-evidence.sha256`은 제외하고 나머지 모든 public asset을 정확히 한
번씩 포함한다. 파일 bytes가 바뀌거나 줄 순서·공백·대소문자가 달라지면
검증이 실패한다.

`release-evidence.json`은 `trio.release-evidence.v1` schema를 사용한다. 주요
필드는 다음과 같다.

- `sourceSha`, `packageVersion`
- `publicAssets`: 이름·byte size·SHA-256을 가진 versioned asset records
- `updaterReferences`: metadata 이름, 참조 파일, declared/actual size와 SHA-512
- `verification`: Windows, macOS, Linux, Pretendard의 sanitized pass summary
- `supportingFiles`: CycloneDX SBOM, 제3자 고지, release notes 이름
- `candidateEvidence`: sidecar와 checksum의 알고리즘·제외 규칙

모든 object key는 재귀적으로 정렬되고 파일은 UTF-8 JSON과 trailing LF 하나로
고정된다. 배열도 스크립트가 정한 filename 순서를 사용한다. evidence 파일의
digest는 JSON 안에 넣지 않고 아래 sidecar로만 기록한다.

```text
<lowercase sha256 of release-evidence.json>  release-evidence.json
```

따라서 promotion workflow는 candidate run ID, tag SHA, source SHA와 함께
`release-evidence.sha256`의 bytes/digest를 고정하고, 공개 직전에 같은 bundle에
대해 `verify`를 다시 실행해야 한다.

## 필요한 sanitized verification 입력

stable 생성은 아래 모든 field가 존재하고 `true`여야 한다. Windows
`digestAlgorithm`은 정확히 `SHA-256`이어야 한다.

```json
{
  "windows": {
    "expectedPublisherMatched": true,
    "authenticodeChainValid": true,
    "digestAlgorithm": "SHA-256",
    "timestampValid": true,
    "appExecutableVerified": true,
    "nsisInstallerVerified": true
  },
  "macos": {
    "developerIdIdentityMatched": true,
    "hardenedRuntime": true,
    "codesignValid": true,
    "spctlAccepted": true,
    "notarizationAccepted": true,
    "staplerValidated": true
  },
  "linux": {
    "updaterDisabled": true
  },
  "pretendard": {
    "cmsValid": true,
    "hashValid": true,
    "publisherAllowed": true,
    "identityMatched": true,
    "glyphCoverageValid": true
  }
}
```

이 JSON에는 certificate/private key, credential, token, password, absolute path,
raw log를 넣지 않는다. 스크립트는 field allowlist와 문자열 검사를 통해 그런
입력을 거부한다. 이 summary가 `true`라는 사실은 실제 SSL.com Authenticode,
Apple notarization, Pretendard CMS, 실장비 QA가 수행됐다는 외부 증거를 대신하지
않는다. 그 증거를 생성·검토하는 단계가 끝나기 전까지 stable은 No-Go다.

Pretendard의 `glyphCoverageValid`는 검증된 packaged TTF의 고정 SHA-256과
SFNT `cmap` format 4/12에서 대표적인 한글 음절·호환 자모·구두점·라틴·숫자
코드포인트가 non-zero glyph ID로 매핑되는지, 그리고 고정 renderer/readiness
회귀 명령이 통과하는지를 함께 확인한다. 이는 package-level smoke evidence다.
실제 페이지가 요구하는 문자·fallback·font metric은 실행 시점의 render-ready
검사에서 별도로 fail-closed로 판단하며, 이 대표 집합의 성공으로 page-specific
coverage를 추론하지 않는다.

## Promotion evidence boundary

The manual promotion workflow is [`.github/workflows/promote-stable.yml`](../../.github/workflows/promote-stable.yml).
It accepts only a numeric candidate run ID, exact tag `v0.1.4`, lowercase
`evidence_sha256`, and exact confirmation `PUBLISH v0.1.4`. Before the protected
delivery App token is created it rechecks the source tag SHA, candidate run
identity/event/conclusion, exact artifact name and expiry, sidecar digest, and
Task 5A evidence. The protected job repeats those checks before creating the
draft Release.

GitHub draft assets cannot be anonymously downloaded. The workflow consequently
does authenticated draft re-query and fresh download first, publishes once,
then fetches public metadata, HTML and every exact asset without App
authentication. An anonymous failure invokes same-step rollback to draft and
fails; the Release may be briefly public during this interval. The workflow
does not claim zero-exposure rollback.

After anonymous verification, it dispatches `trio-release-published` to the
future public delivery repository. The public template
[`trio-releases-attest.yml`](../workflow-examples/trio-releases-attest.yml)
verifies the sidecar/checksum/evidence contract and creates delivery-byte
attestations with explicit subject paths. Attestation proves the bytes served
by the public repository; it does not independently rebuild the private source.

The promotion workflow and public template are code/configuration only in this
checkout. No repository, App, environment, secret, tag, Release or attestation
was created or executed. Stable remains No-Go until those external objects and
real promotion/provenance evidence exist.

테스트는 synthetic bytes로 성공 경로를 확인하고 wildcard/extra asset,
source/project/secret/debug 파일, symlink, traversal·remote metadata, 잘못된
size/SHA-512, 누락 blockmap, Linux update metadata, checksum/evidence digest
불일치, source/version 변경, false/missing platform evidence, non-canonical
JSON/checksum을 fail-closed로 확인한다. 테스트 fixture는 실제 release asset,
인증서, credential 또는 사용자 프로젝트를 포함하지 않는다.
