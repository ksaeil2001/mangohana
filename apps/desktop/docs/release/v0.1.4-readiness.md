# Trio v0.1.4 공개 배포 준비 상태

> 2026-09-17 범위 갱신: 이 문서의 macOS 항목은 **non-MVP / future scope**이며 현재 MVP 지원이나 Release Gate 요구가 아닙니다. Linux 범위는 변경하지 않습니다. [현재 플랫폼 정책](../operations/mvp-platform-scope.md)을 우선합니다.
> 이전 시점의 실행 결과와 gate 상태는 역사적 기록이며 현재 후보 판정은 [최신 Release Gate 보고서](2026-09-17-mvp-release-gate.md)를 따릅니다.

이 문서는 코드·테스트·패키징 결과를 “완료”, “미완료”, “외부 검증 필요”로
분리해 기록합니다. 자동 테스트가 통과해도 실제 Windows 설치·업데이트·서명·
법률 검토가 끝나지 않으면 공개 릴리스 완료로 표시하지 않습니다.

## Gate 1~9 현재 truth set

아래 표의 날짜는 이 문서가 마지막으로 판정된 날짜이며, 외부에서 수행하지 않은
작업을 PASS로 만들지 않는다. 자동 테스트는 해당 gate의 code-side evidence만
증명하며 실장비·서명·법률·GitHub 설정 증거를 대신하지 않는다.

## Gate 4·6·7 code-side closeout record

이 절의 값은 현재 코드·테스트가 보장하는 binding과 아직 관찰하지 못한 live
값을 분리한다. `preview_candidate_run_id`, `preview_evidence_sha256`,
`release_tooling_sha`, `TRIO_APPROVED_RELEASE_TOOLING_SHA`의 실제 값은
설정된 private GitHub Environment와 성공한 run이 생길 때까지 **미정**이다.
따라서 아래 계약을 기록하는 것은 live candidate, signing, public Release 또는
physical QA가 완료되었다는 뜻이 아니다.

2026-08-23 최종 code-side 검증에서 `tests/ci`, `tests/scripts`,
`tests/config` 통합 그룹은 17 files / 155 tests를 모두 통과했다. 단일 fix wave와
재검토 뒤 독립 reviewer의 신규 P0/P1/P2는 없었다. 전체 suite는 위 표와 같이
기존 Windows lock fixture 2건 때문에 계속 BLOCKED이며 Stable No-Go를 유지한다.

### Gate 4 — private preview candidate and transition binding

| 항목 | code-side 계약 / 현재 기록 |
| --- | --- |
| private candidate | `package-release.yml`의 `preview-transition-candidate`가 `0.1.4-preview.1` / `v0.1.4-preview.1`로 고정하고 `--publish never` Windows artifact를 만든다. evidence schema는 `trio.transition-candidate-evidence.v1`이며 `transition-candidate-evidence.json`과 lowercase SHA-256 sidecar를 함께 보관한다. |
| run/artifact/source binding | transition workflow 입력은 `preview_candidate_run_id`, `preview_evidence_sha256`, `release_tooling_sha`다. run은 정확한 workflow identity·`workflow_dispatch`·success·head SHA를 만족해야 하며, artifact는 `trio-preview-transition-candidate-<sourceSha>-<runId>` 하나만 허용한다. private evidence `sourceSha`, run head SHA와 `release_tooling_sha`는 서로 같아야 한다. |
| tooling trust anchor | `release_tooling_sha`는 full commit SHA이고 `TRIO_APPROVED_RELEASE_TOOLING_SHA` Environment variable과 exact-match해야 한다. 실제 Environment 값은 아직 설정·관찰되지 않았다. |
| tracked-tree integrity | transition source와 `.trio-release-tooling` 각각에 대해 `trio.git-source-integrity.v1`, `clean: true`의 `source-integrity-before.json`/`after.json` 및 `tooling-integrity-before.json`/`after.json`을 남긴다. before/after `headSha`와 `treeSha`가 각각 고정·일치해야 하며, 최종 `transition.json`은 이를 다시 binding한다. |
| live blocker | signed preview/transition 설치본과 실제 Windows network, retry, reopen, uninstall을 포함한 WU-01~08 실장비 evidence는 아직 없다. transition baseline이 역사적 v0.1.3 artifact와 bit-identical하지 않을 수 있다는 제한도 유지한다. |

### Gate 6 — anonymous metadata and delivery boundary

promotion code-side contract(`Task 5B2` metadata guard와
`validateReleaseMetadata()` 경계)는 anonymous Release JSON의 `tag_name`을
`v0.1.4`, title을 `Trio v0.1.4`, body를 candidate
`RELEASE_NOTES.md`의 exact UTF-8 bytes, `draft`를 `false`, `prerelease`를
`false`로 검증한다. 생성 요청은 같은 body bytes, `draft: true`,
`prerelease: false`, `generate_release_notes: false`를 사용한다. 검증은
authenticated draft asset re-query/download 뒤 publish하고, public anonymous
metadata·HTML·각 exact asset bytes를 확인한 뒤에만 `PROMOTION_OK=1`이 된다.
anonymous 검증 실패 시 같은 step의 EXIT trap이 Release를 `draft: true`로
되돌리며, rollback 자체가 실패하면 수동 개입을 요구한다. `trio-release-published`
provenance dispatch는 이 검증과 `PROMOTION_OK=1` 뒤에만 실행된다. 현재 public
repository, App, credentials, candidate run과 실제 anonymous bytes는 관찰되지
않았으므로 live signing/delivery는 BLOCKED다.

## 구현 후 focused 검증

2026-08-22 현재 다음 구현 범위가 focused 테스트로 확인되었습니다.

- 승인 기반 페이지 queue: 생성·순차 상태·pause/resume·외부 provider 재개 확인·cancel·실패 페이지 retry·승인 대기 단계 승인·재시작 복원 상태 표시
- 화자/말풍선 v1: 후보 정규화·Character Bank/패널 관계·명시적 사용자 선택·unknown/낮은 신뢰도 review 경계
- render-ready/export: `userTranslation` 전용 식자, revision/fingerprint/geometry/evidence 확인, cleaned asset page/run 소유권과 PASS QA, original/cleaned/typeset 분리 및 ZIP/report/manifest
- focused 결과: 6 files / 29 tests pass; renderer App 전체 200 tests pass; queue panel 4 tests pass

Main IPC export는 모든 typeset page의 동일한 renderer font evidence를 수집하고,
주입된 Main verifier가 해당 identity의 설치 resource를 승인한 경우에만 신뢰
evidence로 승격합니다. verifier가 없거나 identity가 섞였거나 evidence가 불완전하면
기존처럼 typeset 파일을 export하지 않고 실패 report에 남깁니다.

Pretendard v1.3.9의 공식 tag·commit·archive/file SHA-256과 OFL 원문은
`resources/font_ko_fallback/pretendard-1.3.9/`에 고정했고, fixed
`pipeline-resources` packaging과 Main-owned verifier scaffold를 연결했습니다.
하지만 production CMS `.p7s`와 publisher allowlist가 없으므로 verifier는
fail-closed이며 typeset resource evidence를 승인하지 않습니다. 2026-08-23
focused 검증은 IPC·export·resource preflight와 renderer font loader를 포함한
code-side 테스트, typecheck·build 통과이며 production 서명·설치본 결과가 아닙니다.

## 수동 검증 기록 양식

각 Windows 시나리오는 다음 필드를 채운 뒤에만 PASS로 표시합니다.

```text
시나리오:
결과: PASS | FAIL | BLOCKED | NOT RUN
OS/build/권한/DPI:
앱 버전과 설치 artifact:
재현 절차:
관찰 결과:
redacted 로그 경로:
후속 issue:
```
